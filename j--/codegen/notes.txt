[ Problem 1 (Operators)]

Goal: Add analysis and code generation for several operators in our j-- compiler

Approach: To add support for the -= *= /= %= != >= < || ++ -- operators, this involved
modifying multiple files. Firstly, I needed to modify several classes to add support for 
longs and doubles as I implemented these new operators in parser/scanner with long and double
support.

- The following classes were modified to add support for longs and doubles:
    - JNegateOp and JUnaryPlusOp
      - In analyze of both of these methods, I check to see if the operand is of type, INT LONG or DOUBLE
      - Codgen of JUnaryPlusOp was empty and remains empty here
      - In codegen of JNegateOp, I added the correct "addNoArgInstruction" calls depending on the datatype
    - JPlusOp, JMultiplyOp, JDivideOp, JRemainderOp, JSubtractOp
      - In analyze for all of these classes, I check to see if the left hand side of the operator is of type
        INT, LONG, or DOUBLE. I then check to see if the right hand side type matches the left hand side type.
        Then, I set the result type to the type of the right hand side. (Which is the same as the LHS)
      - In codegen of all of these classes, I call the appropriate instructions based on the type.
        For example, if the type was LONG, in JRemainderOp I call LREM or in JDivideOp I call LDIV
    - JPlusAssignOp
      - In analyze, I check that the LHS is either an INT, LONG, or DOUBLE.
        Then I check that RHS has the same type as LHS and set the resulting type to the type of RHS.
      - In codegen, I call the corresponding instruction based on the datatype
        For longs I call LADD, ints I call IADD, and doubles I call DADD
    - JComparisonExpression
      - Here I modify analyze to match the LHS to either an INT, LONG, or DOUBLE.
        Then I check to make sure LHS type = RHS type, and set resulting type to BOOLEAN.
        
- The following classes were implemented to finish adding support for the above operators
  - JMinusAssignOp, JStarAssignOp, JDivAssignOp, JRemAssignOp
    - For all of these classes, analyze and codegen needed to be implemented.
      - Analysis for all of these classes is identical.
        - First I verify that the LHS is an instance of JLhs, and report an error if this isn't the case
        - Then I verify that LHS is either a int, long, or double. I verify that RHS type = LHS type
          and then set the resulting type to RHS.type type
      - Codegen is also quite similar for all of these operators
        - I first load the values using codegenLoadLhsLvalue and codegenLoadLhsRvalue
        - I then call codegen on the rhs value
        - Then depending on the type I call the corresponding instruction.
          For example the instructions for minus assign op had ISUB for ints, LSUB for longs, and DSUB for doubles.
        - If the statement is not a statement expression, I then call codegenDuplicateRvalue
        - Lastly, I call codegenStore on lhs.
  - JNotEqualOp
    - For this class, I referenced JEqualOp to see how the code should be structured
    - In analyze, I simply check that that lhs and rhs have the same type, and set the resulting type to boolean.
    - In codegen I call codegen on the lhs and rhs values
    - In the rest of codegen I call addBranchInstructions based on the datatype of LHS and RHS
    - Reference types and Integers have their own instructions for checking onTrue, while longs and doubles 
      are done in a slightly different way.
    - I first call LCMP or DCMP to compare the long or double, then I use the IFNE or IFEQ instructions when
      determining the value of onTrue
  - JLessThanOp
    - These classes only needed to have codegen implemented.
    - I call codegen on the lhs and rhs
    - Then depending on the type I preform slightly different instructions.
      I compare longs and doubles with LCMP and DCMP.
      I then depending on if onTrue is true or not, I set the instruction in addBranchInstruction to be IFLT or IFGE.
    - Integers are compared using IF_ICMPLT if onTrue is true and IF_ICMPGE otherwise.
  - JGreaterEqualOp
    - These classes only needed to have codegen implemented.
    - I call codegen on the lhs and rhs
    - Then depending on the type I preform slightly different instructions.
      I compare longs and doubles with LCMP and DCMP.
      I then depending on if onTrue is true or not, I set the instruction in addBranchInstruction to be IFGE or IGLT.
    - Integers are compared using IF_ICMPGE if onTrue is true and IF_ICMPLT otherwise.
  - JLogicalOrOp
    - In analyze, I verify that both the LHS and RHS are booleans and set the resulting type to boolean.
    - In codegen, I handle the case where onTrue is true, and where onTrue is false
      - When onTrue is true, I jump to target label if lhs is true. 
        - Then I check if rhs is true, and jump to target label if true.
      - When onTrue is false, I need a bit more logic
        - I first create a label - falseLabel
        - If lhs is true, then jump to falseLabel
        - If lhs is false and rhs is false, jump to target. Otherwise continue to falseLabel.
        - I then add false label to the end of the codegen.
  - JPostIncrementOp and JPreDecrementOp
    - In analyze for both classes, I check to verify that the operand is an instance of JLhs
      - If it isn't I report an error
      - Otherwise, I analyze the operand and verify the type is an INTEGER. 
      - I then set the resulting type to an integer.
    - Codegen of PreDecrementOp
      - Case where operand is a local variable:
        - Get the offset for this variable
        - call output.addIINCInstruction with the offset that was obtained and -1
        - If it isn't a statement Expression, call codegen on its original value
      - Otherwise
        - I first load the values using codegenLoadLhsLvalue and codegenLoadLhsRvalue
        - I then call addNoArgInstruction(ICONST_1)
        - Then I add the ISUB instruction to output
        - If it isn't a statement Expression, call codegen on its original value
        - Then I call codegenStore on the output.
    - Codegen of PostIncrementOp
      - Case where operand is a local variable:
        - Get the offset for this variable
        - If it isn't a statement Expression, call codegen on its original value
        - call output.addIINCInstruction with the offset that was obtained and 1
      - Otherwise
        - I first load the values using codegenLoadLhsLvalue and codegenLoadLhsRvalue
        - I then call addNoArgInstruction(ICONST_1)
        - If it isn't a statement Expression, call codegen on its original value
        - Then I add the IADD instruction to output
        - Then I call codegenStore on the output.
- After doing so, the j-- compiler is now able to handle the above operators.

[Problem 6 (Switch Statement)]

Goal: Add analysis and code generation support for switch statements in our j-- compiler
 
Approach: This problem required the most problem solving and unique code out of every other problem
in this assignment. In order to discuss my own implementation of switch statements, I will begin by
talking about the local variables and analysis. Then I will discuss the two main codegen functions

- Local variables
  - hasBreak and breakLabel are present as discussed in problem 4. Keeps track of where break label 
    should be and if one is present.
  - hi and lo store the highest and lowest switch case values, needed to determine which instruction should be used.
    - initialized to hi = Integer.MIN_VALUE and lo = Integer.MAX_VALUE.
  - nLabels stores the number of labels (not counting the default case) present in the statement.
    - initialized to 0
  - hasDefault tracks if there is a default label in the switch statement. This is needed for handling edge
    cases (discussed in tableSwitch()) 
    - initialized to false
  - opcode stores the instruction code that will be used in codegen.
    - initialized to 0
    - In my implementation if opcode = 0, then that means there is no real case labels or default label
    - In other words, the switch statement is totally empty.

- Analysis
  - Firstly, we push the switch statement onto JMember.enclosingStatement so JBreakStatement can access this instance.
  - Then, a local context is made and used throughout the analysis of the switch statement.
  - Condition is then analyzed and I verify that it is an integer.
  - I check to make sure switchStmtGroups isn't null - meaning there is at least 1 case present
  - I loop through each group
    - I then loop through each label
      - If label is null, then set hasDefault to true and continue (it doesn't count towards nLabels)
      - Otherwise, increment nLabels and analyze the label, and verify it is an integer
      - Then compare the label value to lo and hi, updating them accordingly if it is the new lowest or highest.
    - Then, if group.block() isn't null I run analysis on every statement in the block.
  - This concludes the end of the standard analysis steps of running x.analyze() on anything that needs it.
  - Now I check for a few edge cases.
  - If nLabels == 0 and hasDefault = true, this means there are no real case labels but there is a default case.
    - In this situation I set lo = hi = 0 and opcode to TABLESWITCH
    - Details of how I handle this explained more below in tableSwitch()
  - Otherwise if nLabels is not equal to 0, then that means there is at least one real label
    - In this case determine the correct opcode using the logic given in the discussion slides involving lo, hi, and nLabels.
  - Lastly, pop this off of JMember.enclosingStatement.

- Codegen
  - The codgen function itself for switch statement is quite small, as most of the logic is contained in
    two helper functions discussed after this section of notes.
  - If hasBreak is true, create a label for break statements to jump to
  - Call codgen on the condition of the switch statement
  - Create a label called endLabel - this label will be used if and only if there is no default case in switch statement
  - call the tableSwitch() or lookupSwitch() helper methods depending on the result of codegen.
    - This is where most of the code generation occur
  - add endLabel to the output - after everything generated by thr helper method
  - if hasBreak is true, add breakLabel to output.

- tableSwitch(CLEmitter output, String endLabel)
  - Before I discuss how this code works, I want to note 2 important edge cases that I handle in this helper method.
  - First - unused labels in ArrayList
    - addTABLESWITCHInstruction expects an ArrayList of labels (strings) representing cases in range lo to hi inclusive. 
    - However, if our cases look like (case 1, case 2, case 4) where we skip case 3, the label for what would be case 3 in the array list goes unused.
    - To handle this edge case, I first must check to see what labels in the list won't be used, and I must place their labels before the default label
      so the correct (default) code gets executed. If there isn't a default label present, these unused labels must be placed at the very bottom of the switch 
      statement so they don't accidentally cause unintended code to run. 
    - These labels need to be placed somewhere, or else the labels cannot be resolved when the program code compiles.
  - Second - when there are no real case labels, but there is a default label.
    - addTABLESWITCHInstruction expects at least 1 real case label to be present in our code
    - However in this edge case, no real case labels are present. 
    - To deal with this, I create an ArrayList with a singular "real case label". I also set lo and hi to be 0
    - When I encounter the default case in in tableSwitch I check if we are in this edge case (nLabels == 0)
    - If we are, then I add the label at index 0 of the ArrayList, which is the only label in this array list to output.
    - This satisfies the requirement of addTABLESWITCHInstruction

  - With these edge cases out of the way, I can now discuss the way my code runs.
  - I create two array lists, one to store or labels and another to store what labels are used or unused.
  - I initialize these two arrays with amount (hi - lo) items in the following way
    - labels - I add a new label output from output.createLabel()
    - labelsUsed - I add a false boolean to this array. I assume all labels are unused to start.
  - Then I loop through each label in our switch statement groups
    - If the label is not null (not default), I set the labelsUsed at the corresponding index to true.
  - I then create a defaultLabel which will be used if a default case is present.
  - If there is a default case present, I call addTABLESWITCHInstruction with defaultLabel as the first argument
  - Otherwise, I call addTABLESWITCHInstruction with endLabel as the first argument, as values that are not matched with
    any case should do nothing.
  - I then once again loop through each label of each group
    - If I encounter the default label, and nLabels == 0, I add the only label present in the labels ArrayList (edge case described above)
      I also set labelsUsed to be true as this would not have happened earlier in this edge case.
    - When I encounter the default label, add the unused labels here before adding the default label
    - If I encounter a non-null label, add the corresponding label from labels array list.
  - Once I finish handling the labels, I loop through each statement present in block and run codegen on that.
  - Lastly, If default isn't present, add the unused labels to our output

- lookupSwitch(CLEmitter output, String endLabel)
  - This helper method ended up being much simpler than tableLookup as I did not find any edge cases that needed to be handled here.
  - I declare one TreeMap object mapping integers to strings (case labels to jump labels).
  - I loop through each label in my switchStmtGroups, putting new entries into my TreeMap object.
  - Then I create a default label that will be used if one is present.
  - Call addLOOKUPSWITCHInstruction with defaultLabel for first argument if one is present.
  - Otherwise call it with endLabel.
  - Then loop through each label present in switchStmtGroups, adding the associated label from our TreeMap object
    (or default label if we encounter it)
  - Lastly, call codegen on any statement found in the body of our switch statement group.
